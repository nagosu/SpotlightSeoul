# Phase 5 — 에러/로딩/빈 상태 UI 규칙(공통 UX)

## 목표(Why)
- API 실패/로딩/빈 결과에서 “깨지는 화면”을 없애고, 모든 화면에서 **일관된 UX**로 상태를 표현합니다.
- 이후 기능 Phase에서 상태 처리를 복붙 가능하도록 “최소 세트”를 규칙으로 고정합니다.

## 범위(Scope)
- 화면 공통 상태 3종(`loading`, `error`, `empty`)의 UI/문구/행동 규칙 정의
- 접근성(키보드/스크린리더) 기본 요구사항 포함

## 근거(Evidence)
- `frontend/docs/FRONTEND-UPGRADE-PHASES.md` 2.3(에러/로딩/빈 상태), 4.1~4.3(검증/정책 점검)

## 선행조건(Dependencies)
- Phase 3(HTTP 에러 정규화 정책)

## 작업 체크리스트(아주 상세)
### A. 공통 상태 정의(최소 3종)
- [ ] `loading`: 데이터 로딩 중
  - 버튼/입력은 비활성화(중복 제출 방지)
  - 스켈레톤 또는 스피너(선택) 사용
- [ ] `error`: 재시도 가능한 실패(네트워크/서버)
  - 사용자에게 이해 가능한 메시지 제공
  - “재시도” 버튼 제공(가능하면)
- [ ] `empty`: 결과 없음
  - “결과 없음” + 다음 행동 제안(필터 해제/검색어 수정)

### B. 메시지/문구 가이드(권장)
- [ ] 네트워크 오류: “네트워크 연결을 확인해주세요. 다시 시도할 수 있습니다.”
- [ ] 401/권한: “로그인이 필요합니다.” + 로그인 버튼(또는 자동 이동)
- [ ] 5xx: “일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요.”

### C. 화면별 적용 대상(최소)
- [ ] 목록(메인): 로딩/오류/빈 결과
- [ ] 상세: 로딩/오류(특히 nullable 필드로 인한 크래시 방지)
- [ ] 검색 결과: 로딩/오류/빈 결과
- [ ] 내 북마크/내 주변: 로딩/오류/빈 결과

### D. 접근성(A11y) 최소 기준
- [ ] 로딩 상태는 스크린리더가 인지할 수 있도록 `aria-busy` 또는 라이브 영역 사용(선택)
- [ ] 에러 영역은 키보드 포커스로 접근 가능해야 함(재시도 버튼 포커스 가능)
- [ ] 빈 결과는 단순 문구가 아니라 “다음 행동” 버튼/링크 제공(키보드 가능)

## Definition of Done(DoD)
- 모든 데이터 화면이 `loading/error/empty`를 동일한 방식으로 처리합니다.
- 네트워크 offline에서도 “깨짐” 대신 `error` UI로 정상적으로 전환됩니다.

## 검증 방법
- [ ] DevTools에서 네트워크 offline 후, 목록/상세/검색이 모두 `error` 상태로 표시되는지 확인합니다(원문 2.3).
- [ ] 빈 결과를 만드는 조건(검색어/필터)을 넣고 `empty` UI가 표시되는지 확인합니다.

## 주의/함정
- 상태 UI를 화면마다 따로 만들면 “문구/버튼/동작”이 달라져 QA 비용이 증가합니다. 반드시 공통 규칙(또는 공통 컴포넌트)로 통일해야 합니다.
