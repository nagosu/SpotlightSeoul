# Phase 14 — 자동완성 `GET /festivals/suggest`(입력 UX + 접근성)

## 목표(Why)
- 검색 입력에서 자동완성(suggest)을 제공해 검색 UX를 개선합니다.
- 과도한 네트워크 호출을 방지하고(디바운스/취소), 키보드/스크린리더 접근성을 확보합니다.

## 범위(Scope)
- API: `GET /api/v1/festivals/suggest?q=&limit=` (200) → `{ suggestions: string[] }`
- 입력 디바운스, 요청 취소(최신 입력만 반영), IME(한글 조합) 고려
- 키보드 탐색(↑/↓/Enter/Esc) + aria 적용

## 근거(Evidence)
- `frontend/docs/FRONTEND-UPGRADE-PHASES.md` 3.7(자동완성)

## 선행조건(Dependencies)
- Phase 8(Query) 또는 최소한 공통 HTTP 레이어(Phase 3)

## 작업 체크리스트(아주 상세)
### A. 호출 정책(디바운스/취소)
- [ ] 입력 시 즉시 호출하지 않고 200~300ms 디바운스를 적용합니다(원문 3.7).
- [ ] 요청이 겹치면 “최신 입력”만 반영합니다.
  - 옵션: AbortController(가능한 스택에서) 또는 Query cancelation 전략
- [ ] `q`가 짧을 때(예: 0~1자)는 호출하지 않는 기준을 정합니다.

### B. IME(한글 조합) 고려
- [ ] 조합 중(compositionstart~end)에는 호출을 지연하거나, 조합 종료 시점에만 호출하는 정책을 정합니다.
- [ ] 정책을 문서에 명시해 QA 기준을 고정합니다.

### C. 접근성/키보드 UX
- [ ] 키보드 조작
  - ↑/↓: 항목 이동
  - Enter: 선택(검색 실행)
  - Esc: 목록 닫기
- [ ] aria 적용(최소)
  - 입력: `aria-autocomplete="list"` 등
  - 목록: listbox 역할
  - 항목: option 역할
  - 활성 항목: `aria-activedescendant` 또는 포커스 이동 전략

### D. 에러/빈 상태 UX
- [ ] suggest API 실패 시에도 검색 입력 자체는 사용 가능해야 합니다.
- [ ] 결과가 비었을 때는 목록을 숨기거나 “추천 없음”을 표시할지 결정합니다.

## Definition of Done(DoD)
- 자동완성이 과도 호출 없이 동작하고, 선택 시 검색으로 자연스럽게 연결됩니다(원문 DoD).
- 키보드만으로도 자동완성 선택/닫기가 가능하며, 스크린리더에서도 목록 구조가 인지됩니다.

## 검증 방법
- [ ] `q=서울`로 호출했을 때 Swagger 결과와 동일한 형태로 표시되는지 확인합니다(원문 3.7 검증).
- [ ] 빠르게 타이핑해도 네트워크 요청이 과도하게 늘지 않는지 확인합니다(DevTools).
- [ ] 키보드로 자동완성 항목을 선택해 검색 결과로 이어지는지 확인합니다.

## 주의/함정
- 디바운스 없이 호출하면 입력마다 요청이 발생해 서버/클라이언트 모두 부담이 큽니다.
- 접근성(aria/키보드)을 뒤로 미루면 이후 수정 비용이 크게 증가합니다. 자동완성은 처음부터 규칙을 포함해야 합니다.
