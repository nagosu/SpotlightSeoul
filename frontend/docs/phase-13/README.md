# Phase 13 — 북마크/내 북마크(보호 기능 + 목록 연동)

## 목표(Why)
- 북마크 토글과 “내 북마크 목록”을 Bearer 인증 기반으로 구현해, 사용자 개인화 기능을 완성합니다.

## 범위(Scope)
- 북마크 토글: `PUT /api/v1/festivals/{id}/bookmark` (Bearer, 200) → `{ bookmarked }`
- 내 북마크: `GET /api/v1/users/me/bookmarks?page=&size=` (Bearer, 200) → `FestivalPageResponse`
- 대상(원문 기준): 상세 또는 카드에 북마크 토글 UI, 신규 “내 북마크” 페이지 + 라우팅

## 근거(Evidence)
- `frontend/docs/FRONTEND-UPGRADE-PHASES.md` 3.6(북마크/내 북마크)

## 선행조건(Dependencies)
- Phase 6(로그인), Phase 7(401/복귀), Phase 8(Query), Phase 9(목록 렌더러)

## 작업 체크리스트(아주 상세)
### A. 토글 UI 위치 결정(원문 3.6)
- [ ] 상세(Detail)에서 제공할지, 카드(PostCard)에서 제공할지 결정합니다.
- [ ] 결정 기준을 문서에 남깁니다.
  - 상세만: 구현 단순, UX는 상세 중심
  - 카드까지: UX 향상, 캐시 동기화 난이도 상승

### B. 비로그인/401 UX(필수)
- [ ] 토큰 없으면 로그인 유도 + 복귀(returnTo)
- [ ] 401이면 토큰 제거/로그인 유도(Phase 7)

### C. 내 북마크 화면/진입점 추가(보호 라우트)
- [ ] 신규 페이지를 추가하고, 라우팅에 연결합니다(원문 3.6).
- [ ] 보호 라우트 정책을 정합니다.
  - 비로그인 접근 시 로그인으로 이동 + returnTo

### D. Query 표준 적용
- [ ] 내 북마크 queryKey 고정: `['auth','me','bookmarks', {page,size}]`
- [ ] 토글 mutation 후 캐시 동기화
  - 상세 캐시/내북마크 캐시/목록 캐시 중 어떤 것을 invalidate/setQueryData 할지 문서에 명시

### E. 북마크 “초기 상태” 전략(중요, 원문 3.6)
- [ ] 옵션 A(정확): 내 북마크 목록을 캐시하고 id 포함 여부로 초기 표시
- [ ] 옵션 B(단순): 최초에는 미확정 상태로 두고 토글 후에만 반영
- [ ] 선택한 전략과 이유(정확성 vs 구현 복잡도)를 문서에 남깁니다.

## Definition of Done(DoD)
- 내 북마크 화면에서 페이징 조회가 가능하고, 토글 결과가 즉시 UI에 반영됩니다(원문 DoD).
- 비로그인/401 케이스에서 로그인 유도 및 복귀가 동작합니다.

## 검증 방법
- [ ] 토큰 있음: 토글 → 내 북마크 목록에 반영 확인
- [ ] 토큰 없음: 내 북마크 접근/토글 시도 → 로그인 유도 → 로그인 후 returnTo 복귀 확인
- [ ] Swagger `Authorize`로 동일 API 호출 결과와 프론트 UI를 비교합니다.

## 주의/함정
- “초기 상태” 전략을 정하지 않으면, 사용자는 북마크가 눌렸는지/아닌지 혼란을 겪습니다. 문서에서 반드시 선택해야 합니다.
