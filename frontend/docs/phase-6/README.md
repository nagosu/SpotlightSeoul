# Phase 6 — 로그인/회원가입(실제 API 연동) + 폼 UX

## 목표(Why)
- 현재 “화면 이동만 있는” 로그인/회원가입을 실제 API 계약에 맞춰 연동합니다.
- 인증이 필요한 기능(좋아요/북마크/내 북마크)을 위해 **토큰 발급(로그인) 경로**를 먼저 확보합니다.

## 범위(Scope)
- 회원가입: `POST /api/v1/users` (201)
- 로그인: `POST /api/v1/login` (201) → `access_token` 반환(프론트는 `accessToken`)
- 폼 UX: 입력 검증, 중복 제출 방지, 에러 메시지/로딩 처리
- 로그인 성공 후 동선(기본 이동/returnTo는 Phase 7에서 고정)

## 근거(Evidence)
- `frontend/docs/FRONTEND-UPGRADE-PHASES.md` 3.4(인증), 2.2 주의(201 성공)

## 선행조건(Dependencies)
- Phase 3(HTTP 레이어), Phase 5(로딩/에러 UX 규칙)

## 작업 체크리스트(아주 상세)
### A. API 계약 확인(스웨거 기준)
- [ ] `POST /api/v1/users` 요청/응답 스키마, 성공 코드가 201인지 확인합니다.
- [ ] `POST /api/v1/login` 요청/응답 스키마, 성공 코드가 201인지 확인합니다.
- [ ] 응답 키가 `access_token`인지 확인하고, 프론트 내부에서는 `accessToken`으로 사용할 계획을 명시합니다(Phase 4).

### B. 폼 입력/검증 규칙 정의
- [ ] 로그인 입력: 이메일/비밀번호 형식 검증(최소한 빈값 방지)
- [ ] 회원가입 입력: 스펙에 맞는 필드 검증(최소한 빈값 방지)
- [ ] 제출 중 상태에서는 버튼/입력을 비활성화합니다(중복 제출 방지).

### C. 로딩/에러 UX 적용(Phase 5 규칙)
- [ ] 제출 중 `loading` 상태 표시(버튼 로딩 등)
- [ ] 실패 시 `error` 메시지 표시(가능하면 인라인)
- [ ] 성공 시 다음 동선으로 이동(기본: 홈), 단 `returnTo` 복귀는 Phase 7 정책을 따릅니다.

### D. 상태코드 201 성공 처리(치명 포인트)
- [ ] 로그인/회원가입 요청은 201을 성공으로 처리해야 합니다(원문 2.2 주의).
- [ ] HTTP 레이어/Query 레이어 어디에서든 “201을 에러로 처리하지 않도록” 체크리스트에 명시합니다.

### E. 후속 범위(권장, 원문 3.4의 “추가로 고려할 화면”)
이 Phase에서 당장 구현하지 않더라도, 문서에 선택지로 명시해 후속 작업 범위를 명확히 합니다.
- [ ] 회원수정: `PUT /api/v1/users`
- [ ] 회원탈퇴: `DELETE /api/v1/users/{id}` (204)

## Definition of Done(DoD)
- 로그인/회원가입이 스웨거 계약대로 동작하며, 201 성공 응답을 정상 처리합니다.
- 실패/로딩/빈 입력 등의 케이스에서 UX가 깨지지 않습니다.
- 로그인 성공 시 토큰이 확보되어(저장 정책은 Phase 7) 인증 필요 기능을 진행할 준비가 됩니다.

## 검증 방법
- [ ] Swagger UI에서 동일한 요청을 수행해 201/응답 본문 형태를 확인한 뒤, 프론트에서도 동일하게 성공 처리되는지 비교합니다.
- [ ] 잘못된 입력(빈값/형식 오류)을 넣었을 때 제출이 막히거나 인라인 에러가 노출되는지 확인합니다.

## 주의/함정
- `POST /login`과 `POST /festivals(검색)`은 201 성공이라는 점을 놓치면 “로그인이 항상 실패”처럼 보일 수 있습니다.
- 토큰 저장 위치/401 복귀 동선은 Phase 7에서 반드시 일관되게 고정해야 합니다(이 Phase에서 임시로 섞지 않습니다).
